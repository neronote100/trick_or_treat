# ハロハロおかしラリー / Trick or Treat Collection

noteで活動する参加者が、自分のキャラクターを使ったお菓子屋さんを開き、
ほかのお店を巡ってお菓子を集めるハロウィン企画サイトです。

## サイトのタイトルとトップ画像

サイト名・ブラウザタイトル・note等のOGP表示は「ハロハロおかしラリー」に統一しています。トップのキービジュアルは `public/halo-oka-rally-banner.webp`（1536×804、横長・文字入り）。初めての訪問者は画像とイベント案内を見た後、note IDを登録して図鑑やお店作成を利用できます。既存のnote ID・ガチャ・図鑑データは変更しません。

## 企画の基本体験

1. note IDを入力して参加する
2. 自分のお店に、各自のAIで作ったキャラクター画像とお菓子画像を登録する
3. `https://<site>/shop/<note-id>` の専用URLを共有する
4. 訪問者が「トリック・オア・トリート！」を押す
5. その店に登録されたお菓子から1つがランダムで当たる
6. 初めて入手したお菓子が自分の図鑑に保存される
7. 異なる10・20・30店舗でゲートを突破し、続いて現れる隠しステージ（50・75・100店舗）へ進む
8. 各ゲートで、王子が登録した特別画像を解放する（最終目標は100店舗）

抽選回数に制限は設けません。同じお菓子が重複して出ても、図鑑では1種類として記録します。
ゲートは異なる店舗数で判定します。100店舗は報酬の最終目標であり、達成後もほかの店舗の訪問や抽選は可能です。

## お店別コンプリートマーク

- 図鑑の「訪れたお店」に限り、登録された全ての公開中（有効）のお菓子を1種類ずつ入手すると、カードに金色の「✦ コンプリート！」マークを付けます。
- 未達成の店に総種類数・残り種類数を表示しません。お店のガチャ画面の「？」は固定3個の飾りで、種類数を表しません。公開のお店取得APIにも総種類数を返しません。
- **店主が新しいお菓子を追加したら、未入手の参加者のコンプリートマークは消えます。** 新しい種類をすべて集めると、再び表示されます。
- 現在有効な種類のみで毎回判定するため、追加・削除・無効化にも追従します（お店自体に有効なお菓子が0種類の場合はコンプリート扱いにしません）。
- 導入前に全種類を集めていた参加者も、図鑑を開くと現在のお菓子構成に基づき判定されます。
- 旧実装の `shop_completions` テーブルとマイグレーションは既存DBとの互換性のため残しますが、表示判定には使用しません。

## 3枚合体イラスト（10・20・30店舗）

管理画面の「3枚合体イラスト（3:1）」へ**横3:縦1の画像を1枚**登録するだけで、ブラウザが左・中央・右の1:1画像を自動生成して一緒に保存します。手作業の分割は不要です。

図鑑の表示位置と解放順は意図的に異なります。

| 到達店舗数 | 解放する欠片 | 図鑑での位置 |
| --- | --- | --- |
| 10 | 左 | 左 |
| 20 | 右 | 右 |
| 30 | 中央 | 中央 |

図鑑の並び順は **10（左）・30（中央）・20（右）** です。30店舗達成で完成した**3:1画像**を図鑑の専用枠に表示します。

- 完成画像は3:1比率（例：3600×1200px）、PNG / JPEG / WebP / GIF、ファイルサイズ5MB以下
- 1回のアップロードから完成画像＋3パネルを保存し、到達前のパネル画像や完成画像のURLはAPIで渡しません
- 管理者が画像を差し替えると、達成済みの参加者も図鑑を開くだけで新しい画像が表示されます
- 画像が未登録でも10・20・30店舗の達成記録は保存され、あとから登録可能です
- **10・20・30店舗のゲート報酬と3:1画像は自動同期します**。10=左、20=右、30=中央。ゲート画像を別途アップロードする必要はありません
- 以前に3:1画像を登録していても、管理画面の再表示または図鑑の表示時にゲート報酬枠を自動修復します。再アップロードは不要です
- 3:1登録後は10・20・30店舗の手動差し替えを禁止し、画像の食い違いを防ぎます。50・75・100店舗の独立報酬は従来どおり管理できます
- 古い個別報酬はDB内に保持して非表示にし、同期後の3枚を現行のゲート報酬にします
- 既存のCloudflare D1には `triptych_illustrations` テーブルを自動追加します。SQLマイグレーションも `migrations/0002_triptych_illustration.sql` に用意しています

## アカウント方針

メールアドレスやパスワードは収集しません。公開上の識別子にはnote IDを使います。訪問・抽選・図鑑は、ブラウザが変わってもnote IDだけで利用できます。

この企画では手軽さを優先し、参加者の本人確認は行いません。note IDを入力すれば、どのブラウザからでも同じ参加データと店舗編集画面へ入れます。note IDは公開情報のため、なりすましを完全には防げない前提の運用です。

- 参加ID: note IDのみ
- 訪問・図鑑: note IDのみ
- 店舗作成・編集: note IDのみ
- 引き継ぎコード: 使用しない
- 管理画面: Cloudflare Secretの `ADMIN_TOKEN` を王子専用パスワードとして使用
- 出店公開: 必要な画像を登録して「出店する」を押すと即時公開

詳細は [docs/identity-and-collection.md](docs/identity-and-collection.md) を参照してください。

## 管理者向け登録お菓子数

`/#/admin` で管理者キーを入力すると「🍬 登録済みのお菓子」に以下の実データを表示します。

- **登録総数**：全店舗に保存されているお菓子画像の件数（非公開・無効状態も含む）
- **有効なお菓子**：`is_active = 1` の登録件数
- **1店舗の最多**：現在もっとも登録数が多い1店舗のお菓子数
- **登録のある店舗**：1個以上お菓子を保存している店舗数
- 下の「みんなのお店」では各店舗のお菓子の登録数を表示（既存機能）。
- 集計は認証済み管理者専用 `GET /api/admin/shops` のレスポンスにだけ含まれ、ガチャ・図鑑・公開お店APIには全種類数を出しません。
- 現在のアップロード制限は**画像1枚5MBまで**、お菓子の登録個数には制限なし。Cloudflare KV無料枠は保存1GB・読み取り10万件/日・書き込み1000件/日なので、特に画像枚数と実容量を見ながら個数・サイズ制限の変更を判断してください。自動画像圧縮や容量監視は今回未実装です。

## 管理者向け参加者一覧（お菓子収集状況）

`/#/admin` で管理者パスワードを入力すると、画面の上部に **「🍬 参加者・お菓子収集状況」** が表示されます。登録されたnote IDすべて（未出店・未収集を含む）を表示します。

- **訪問店舗**：図鑑に残っている異なる出店者の店舗数
- **お菓子の種類**：図鑑に残っている異なるお菓子数
- **取得回数**：図鑑に残っているお菓子の取得回数合計（重複ガチャを含む）
- 登録日、本人の出店状態、達成ゲート、noteプロフィールへのリンクも表示
- デフォルトは訪問店舗数が多い順。note ID検索（部分一致）、**25 ID／ページ**でページ切り替え
- 登録ID数・収集開始ID数の全体件数を表示。検索した場合は検索に一致する件数も表示
- `GET /api/admin/participants?page=1&q=... ` は `x-admin-token` の管理者認証が必要で、未認証では401
- 参加者情報は現在の図鑑に残る記録が対象。お店・お菓子が削除されると集計値も減少します
- 登録IDは本人確認をしていないため「実在する本人の数」ではありません
- 新しいテーブルやマイグレーションは不要。既存の `users`、`collection_items`、`treats`、`shops` を参照します

## 画面

- `お店をひらく`: 店名、キャラクター、お菓子を登録してそのまま出店
- `図鑑`: 訪れたお店、入手したお菓子、重複数、100店舗までのゲート進捗、特別画像
- `管理`: 全店舗の確認・公開停止・削除、ゲート別特別画像の登録・差し替え（`/#/admin`）

メイン操作は画面下の「お店をひらく」「図鑑」の2メニューへ集約しています。公開店舗の全体一覧は表示せず、参加者から届いた専用URLを開いて訪問します。一度お菓子を受け取ったお店だけが図鑑の「訪れたお店」に追加されます。
管理画面の入口は「お店をひらく」画面の最下部にだけ表示します。

## 技術構成

- フロントエンド: モバイルファーストのWebアプリ
- API: Cloudflare Workers
- データベース: Cloudflare D1
- 画像保存: Cloudflare Workers KV（無料枠）
- 配信: Cloudflare Workers / Pages

画像生成APIは使用しません。お菓子画像は参加者が各自のAIで作成し、完成画像をアップロードします。

## 画像容量を抑える WebP 化（2026-10-25）

- PNG・JPEG画像を新しく登録するときは、**ブラウザ側でWebPに変換してから保存**します。お菓子画像は長辺1400px、店舗キャラは1600px、特別報酬は1600px、合体完成イラストは3000pxを上限とし、WebP品質82%を基本にします。WebP化で元ファイルより大きくなる場合は元形式を保持します。
- アニメーションを壊さないためGIFは対象外。すでにWebPの画像も無駄な再エンコードをしません。
- 既存画像は管理者専用 `/#/admin` の「既存画像のWebP軽量化」から **「残りをまとめてWebP化する」** を一度押すと、自動的に20枚ずつ順番に読み込み **1回最大300枚** を連続処理します。途中停止・進捗確認・スキップ／エラー件数表示にも対応します。希望者は従来の「20枚だけ試す」も使えます。300枚以上の場合は無料枠保護のため停止し、残りは別日に再実行できます。
- PNG・JPEGだけを対象にブラウザで変換し、新しいKVキーへ保存してからD1の参照キー（店舗・お菓子・報酬・合体イラスト）を一括更新します。**元画像はすぐ削除せず、移行履歴とともに24時間以上保持**します。管理画面から元に戻せます。
- 元画像の整理は管理者が24時間以上経過後に手動で実施。「24時間以上経過した元画像をまとめて整理する」で最大300枚を順番に整理できます。各画像を削除する前に、WebPがKVにあること、元画像のDB参照が残っていないことを確認します。変換直後はバックアップからの表示補完と復元に対応します。
- 変換後が大きくなるファイルは移行せずに残します。変換に失敗しても他の画像の変換は続けられます。作業中は管理画面を閉じないでください。
- この機能は本番の保存済み画像をGitHubマージ時に自動変換しません。管理者ログインと「残りをまとめてWebP化する」ボタンの1回の操作で開始します。変換はブラウザ内で処理するため、終了まで管理画面のタブを開いた状態にしてください。ブラウザの終了やスマホの画面オフでは中断する可能性があります（完了済みの画像は保持）。
- 無料枠のKVには1GB容量上限、1日1000書き込み・10万読み取りなどの上限があります。容量超過時は新画像の保存に失敗しますが、読み取り制限に達すると既存の画像表示にも影響します。移行は1件につきKVの読み取りと書き込みが発生し、元画像の削除は24時間経過後の別操作です。安全上限は1操作300枚であり、毎日の実際の残余枠・KVストレージ残量はAPIで確認していないため、容量や日次回数に達した場合は中断します。
- 実際のKVの残り容量や全画像の移行完了を示すものではなく、サイトのDBが現在参照しているPNG・JPEG画像を一覧化する仕組みです。

## 🎃 ハロハロ・ラストレター 💌（7人版）

- **管理画面** `/#/admin` の「ハロハロ・ラストレター」から初期化すると、変更されない7つの専用URLをランダム発行します（`/letter/<32桁のランダムID>`）。それぞれのクリエイターに自分のURLを渡し、note記事へ貼ってもらいます。
- **1人につき表面1枚・裏面1枚（どちらも1:1のWebP）**を7人分、計14枚登録します。**メッセージ文言は未決定**のため、管理画面の登録欄・プレビューや参加者画面には、仮の固定文字列・各人の文字割り当てを表示しません。7枠それぞれの表面・裏面は独立して変更でき、管理画面で並べてプレビューできます。既存のURL・DBの収集記録は変更しません。
- **初期状態は非公開**。7人全員の名前・表7枚・裏7枚と最後の4:5の特別イラストの計15枚を登録した後に公開可能です。非公開時は参加者に文字・画像などを返しません。既存URLは変わりません。
- 公開後、記事の専用URLを開いた人は、既存のnote IDで参加していれば**1文字を自動取得**。未参加ならnote ID登録後に元のURLへ戻って受け取れます。各参加者の取得状態はD1の `last_letter_claims` に保存。同じURLを何度開いても重複カウントされません。
- 専用の収集ページは `/#/last-letter`。初期リリースではメインナビ／お菓子図鑑からのリンクは貼らず、管理画面と記事からのみアクセスできる**ソフトローンチ**です。
- 未取得の文字は「？」の正方形カード。取得した文字には、管理者がWebPで登録した**完成イラストを切り抜かず、そのまま表示**します。サイトが別の文字や手持ちボードを重ねることはありません。
- **縦1列レイアウト（PC・スマホ共通）**：7人を1行ずつ表示し、左側にクリエイター名・獲得した文字・URLリンク、右側に1:1のイラストを配置します。管理者プレビューでは画像登録前も名前と専用URLが見えます。参加者には発見済みのクリエイターのnoteプロフィールリンクのみ表示し、未発見の専用URLは公開しません。管理画面の7人の登録カードも縦1列、各行の左に名前とURL、右に表面・裏面のプレビューです。
- **登録画像の形式**：表面7枚・裏面7枚は各1:1（推奨1024×1024px）、最後の特別イラストは4:5（推奨1000×1250px）。すべてWebP、1枚5MB以下。ブラウザで比率チェック、サーバーでWebP形式と容量を検証します。元画像は加工・再圧縮せず保存します。
- **特別な最後の1枚**は7枚とは独立した**4:5の縦長WebP**（推奨1000×1250px・5MB以内）を管理画面の「最後の特別イラスト」でアップロードします。
- 管理画面で「画像の下に添えるメッセージ」（例：遊んでくれてありがとう✨）と「添える文章」を自由に編集できます。**最後の4:5イラストには文字を重ねず、画像を加工せずそのまま表示**し、メッセージは画像の外に配置します。
- 7枚集めて反転ボタンを押すと、**7枚の表面イラストが各人の登録済み裏面イラストへ反転**。キラキラとお菓子が舞ったあと、独立した4:5の特別イラストと画像の下のメッセージが現れます。動きを減らす設定ではアニメーションを控えます。
- **公開条件は合計15枚**：表面7枚・裏面7枚・最後の1枚。未達成者は裏面画像のURLや特別イラスト・メッセージをAPIから取得できません。すでに配布したURL・取得進捗は一切変更しません。
- D1への追加は非破壊的な `last_letter_backs` テーブルのみ（`migrations/0007_last_letter_backs.sql`）。Workerは初回APIアクセス時にも自動作成し、既存の表面画像・収集履歴・最後のイラストを変更しません。
- **7文字すべて集まると**収集一覧の**上と下の両方**に「7枚のボードをひっくり返す」ボタンが現れます。押すと7枚の裏面WebPに反転し、お菓子が降る演出と特別な最後の1枚を表示します。スマホで上のボタンを押した場合も、反転後の特別イラストへスクロールします。
- 管理者API：`GET /api/admin/last-letter`, `POST /api/admin/last-letter/initialize`, `POST /api/admin/last-letter/slot`, `POST /api/admin/last-letter/visibility`。一般参加者API：`GET /api/last-letter`, `POST /api/last-letter/claim`。公開APIから未取得の文字や共有トークンのリストは取得できません。
- D1マイグレーション：`migrations/0005_last_letter.sql`。アプリの起動時にもテーブルを作成するため、既存ラリーには破壊的な変更はありません。
- 注意：本サービスのnote IDは本人認証ではなく入力されたIDによる管理です。別人がIDを入力できる点は、既存お菓子ラリーと同じ仕様です。

## ローカル起動

```bash
npm install
npm run db:migrate:local
npm run dev
```

構文確認と一連のAPIテスト:

```bash
npm run check
npm test
```

## Cloudflareへ公開

1. Cloudflareへログインします。

```bash
npx wrangler login
```

2. 管理者キーを登録します。

```bash
npx wrangler secret put ADMIN_TOKEN
```

3. 公開します。D1とKVは初回デプロイ時に自動作成され、テーブルは最初のAPIアクセス時に初期化されます。

```bash
npm run deploy
```

CloudflareのGit連携でも、D1とKVは自動作成されます。公開後にWorkerの設定から `ADMIN_TOKEN` をSecretとして登録してください。
